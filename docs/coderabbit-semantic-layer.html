Deep-research teardown · Architecture

The semantic layer behind a pull request

How CodeRabbit turns a flat, alphabetical diff into a graph of the change — and whether one developer can build the same thing.

CodeRabbit teardown · compiled 2026-07-18 · sources: vendor blogs + LanceDB case study
01

The core idea

GitHub shows you a diff: files in alphabetical order, every line a delete or an add. CodeRabbit throws that ordering away. For each PR it rebuilds the change as a graph — syntax from the AST, meaning from the call and dependency edges — then re-renders that graph the way the author would actually walk you through it. The claim, in their words: reconstruct "how the PR author would have crafted the diff."

02

The pipeline, end to end

Six loosely-coupled stages. Amber marks where the semantic work happens; teal is live retrieval; violet is the persistent memory that sits off to the side.

◇
Trigger

Ingest & clone

A webhook fires when a PR opens on GitHub or GitLab. CodeRabbit clones the repo and isolates the diff.

Solo-dev read: standard, well-trodden. A weekend.
{ }
Syntax

Parse to an AST

tree-sitter / ast-grep parse the code structurally, so a change reads as "method calculate_total in class Cart changed" — not "line 10 changed." Diff hunks are expanded out to their enclosing function.

Off the shelf. tree-sitter has ~40 grammars + mature bindings.
⧉
Semantic · core

Build the change graph

Nodes are symbols; edges are calls, imports and dependencies — traced cross-file and cross-repo. This is the "semantic" in semantic layer: structure the model can reason over instead of raw text.

The hard, disclosed-vaguely part. What makes an edge "semantic" is not published.
⌕
Retrieval · context engine

Gather context + static analysis

Graph-based retrieval over ASTs, dependency graphs and call relationships pulls in related code beyond the diff. Diagnostics from 25–40+ linters & SAST tools are fed in as structured signal.

Static analysis isn't a separate product — it's one input to the prompt.
☰
Semantic · the payoff

Cohorts, layers & the walkthrough

Related changes are grouped into cohorts, ordered into dependency-aware layers (foundational changes first), each given a plain-language summary — plus a Mermaid diagram where one earns its place. Moved code renders as a single relocation, not a delete + re-add.

This is the moment users feel. "Oh — it actually understands my PR."
⛁
Persistent memory · off to the side

Cross-PR RAG (LanceDB)

A separate, standing vector store indexes the whole codebase for cross-PR memory — past PRs, Jira/Linear tickets, team conventions — queried semantically. Reported at millions of reviews with sub-second latency.

Defer this. It's the moat and the cost — not needed to ship the feel.

04

The cut line

"Build the per-PR pipeline. Skip the persistent cross-PR infra until you have users."

  1. Skeleton. Webhook → clone → tree-sitter parse → hunk-to-symbol mapping.
  2. The semantic layer people feel. Per-cohort LLM summaries + a dependency-ordered walkthrough. This alone lands the effect.
  3. Perceived polish. Move-aware diff rendering — contained scope, high payoff.
  4. Diagrams, gated. LLM → Mermaid for call flows & data models, behind an "is this worth it" check.
  5. Later — once repos are worth remembering. LanceDB cross-PR memory + the cost-saving cheap-model dedup on incremental reviews.

Steps 1–4 are a 1–3 month solo build for a competent engineer and already deliver the "this understands my PR" moment. Everything expensive is exactly what you can defer.

05

Where it slots into Olympus

Olympus already runs an orchestrator / worker / reviewer loop over an issue frontier — a strong substrate. The semantic layer is a Reviewer capability, not new standing infrastructure.

Reviewer

Natural home for the pipeline — it already sits at the review stage and can emit a structured walkthrough artifact.

Orchestrator

Surfaces the per-PR graph + cohort walkthrough to the frontier without any persistent index behind it.

Repair loop

The cheap-model semantic dedup maps cleanly onto re-review cycles, where the same PR is reviewed repeatedly.

Bounded steps

Olympus favors recoverable steps — so start with ephemeral per-PR graphs, add durable memory only when it's earned.
